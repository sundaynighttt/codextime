# Windows 0.4.1 — bounded memory and log retention

This Windows maintenance build replaces a locally installed 0.2.0 prototype with
the current Windows implementation and bounds CLI response and log growth.
It is a local maintenance candidate, not a new public GitHub Release.

## Observed failure

- Windows recorded 31 resource-exhaustion events on 2026-10-21, with
  `CodexTime.exe` committing up to 47,926,530,048 bytes (44.64 GiB).
- A bounded sample of the old 3,740,272,851-byte log contained 861 identical
  `XamlParseException` entries in approximately 1.09 seconds. The exception
  rejected a TwoWay/OneWayToSource binding to the read-only `RemainingPercent`
  property of an anonymous object.
- This is evidence of a repeated UI failure in the same period as the memory
  exhaustion. No process heap dump was captured, so the exact allocation chain
  behind the 44.64 GiB peak is not claimed as proven.
- The current detail view creates text directly from immutable usage snapshots.
  It has neither that read-only TwoWay binding nor the legacy dispatcher handler
  that continued after the repeated error. Private logs and account data are not
  included in this repository.

## Changes

- Read JSONL responses in a fixed buffer and reject a line while reading once it
  exceeds 262,144 characters. The previous check ran after `ReadLineAsync` had
  already allocated the complete line.
- Keep stderr draining in fixed buffers with the request cancellation token and
  verify timeout/cancellation cleans up the owned process tree.
- Limit a log message to 2,048 characters. Retain the current log and one archive,
  each no larger than 1 MiB. Upgrading an oversized existing log copies only its
  bounded tail and reclaims the old file on the next normal app startup.
- Exercise the actual detail view through 500 updates and layout passes, checking
  stable element counts and retained managed-memory growth below 32 MiB.

## Validation

- .NET 8 Release build, parser, provider HTTP/storage, lifecycle and UI checks.
- 500 detail updates: 19 KiB retained managed-memory growth in the first local run.
- Synthetic stream boundary, LF/CRLF/EOF, active cancellation, 4 MiB stderr flood,
  oversized stdout, EOF with open stderr, timeout and child/descendant cleanup.
- Log rotation, bounded multibyte messages, concurrent writes, and recovery from
  a 3 GiB sparse log without allocating or reading 3 GiB.
- Self-contained Windows x64 package self-tests and four synthetic WPF previews
  passed. The packaged run retained 0 KiB after 500 detail layout updates.
- Installed locally with the original taskbar display mode and Codex-only setup;
  startup now targets the corrected installation. Previous binaries and settings
  were backed up before replacement. The running executable hash matches the
  packaged executable.
- Six samples across 50 seconds after startup: private memory 68.06–68.13 MiB,
  CPU time increased by about 0.22 seconds, and the active log remained 90 bytes.
  The retained old log tail is 1,048,372 bytes; the old 3.74 GB file was reclaimed.
- The live taskbar overlay did not expose a targetable automation window in this
  desktop state. Synthetic rendering and process checks passed; real-account
  values were not independently compared against the provider's usage page.
